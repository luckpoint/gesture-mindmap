# Web Speech APIによる音声入力の検討

2026年10月24日。状態：ノードへの接続とハンド追加時の音声入力・サムアップ左右による確定／取消を実装。Chromeのlocalhostではタイマー修正後の動作をユーザーが確認。指示欄への接続・Safari実機・ステージングHTTPSの検証は未完了。

## 今回の実装（2026年10月24日）

今回の要望に合わせ、以下の仕様は本文の初期提案より優先する。

- 手の追加ジェスチャーで空ノードと編集を開き、標準で日本語の音声認識を開始する。カメラパネルの有効化チェックは撤去。発話終了後は下書きを保持し、サムアップを鏡像の画面左に倒して600ms保持するとOK（確定）、画面右に倒して600ms保持するとNo（取消）。追加＋文字確定は1回のUndoにまとめる。次の追加も新しい短い認識セッションとして開始し、常時待ち受けや自動再試行はしない。
- 手で追加した編集パネルは、聞き取り中の停止ボタンを省き、左にOK・確定、右にNo・取消を配置する。聞き取り中のOKは停止後の最終結果を待ち、正常終了かつ文字があれば確定する。Noは即座に中断して新規ノードを取り消す。通常終了だけでは確定しない。失敗時は再開ボタンと手入力へ戻れる。フォーカス離脱だけでは確定しない。
- 通常の追加・書きかえでは編集パネルの「音声入力（日本語）」から開始する。最終結果を末尾へ追加し、終了後も編集を維持する。「確定」またはEnterで反映、「取消」またはEscapeで取り消す。編集中のTabは音声ボタンへ移動する。
- 手で追加した場合も、拒否・無音・認識エラー・時間切れでは自動確定しない。既存下書きと受信済み最終結果を保持し、手入力やマイクボタンから再開できる。ブラウザがジェスチャー起点の開始を認めない環境もボタン操作へ戻れる。
- 認識中は通常の手の操作と対象の手入力を抑止する。手で追加した編集に限って確定／取消の左右ジェスチャーを受け付け、選択・移動・追加・削除・ズームは抑止する。途中結果は別表示し、ノードへ保存しない。停止は最終結果を待ち、取消・編集終了・ページ離脱・タブ非表示では中断して遅延イベントを無視する。権限ダイアログによるwindow blurだけでは音声を中断しない。
- `speech/controller.js` に認識の状態・対象検証・開始15秒／停止5秒／聞き取り60秒の上限を分離した。音声データをアプリから保存・アップロードする処理は追加していない。開始前にブラウザの音声処理について表示する。
- `_headers` は `microphone=(self)` に変更。カメラ・位置情報の方針は維持。配信・権限・実認識の成立性は未検証で、変更だけで動作保証とはしない。
- 指示欄のマイクUIと4000文字超過の確認UI（本文の段階3）は今回は未実装。既存のOS標準音声入力は利用できる。
- Chromeで開始前に発生した `Illegal invocation` は、タイマー関数をControllerのメソッドとして呼んだことが原因。既定のタイマーを `globalThis` 経由の関数で包み、ブラウザの呼び出し先制約を再現する回帰テストを追加した。ユーザーが動作を確認済み。今回の左右ジェスチャーの実カメラ確認は別途必要。

実ブラウザ自動化はChromeプロセスが起動直後にSIGABRTで終了し、代替のブラウザ接続も利用不可だったため未完了。

自動テストでは偽APIによる結果差し替え・重複防止・停止・中断・遅延イベント・対象変更・タイムアウト、UIの音声確定とUndo/Redo、取消・失敗時の編集維持、フォーカス範囲とタブ非表示を検証する。実音声の精度、初回許可、Safari対応は実機確認が必要。

## 1. 結論

Web Speech APIの音声認識を追加する。マイクボタンから開始し、認識した文字を確認・修正して通常の編集操作で確定する方式を推奨する。初期版は短い発話を1回ずつ入力し、常時待ち受けや音声による自動送信は扱わない。

ユーザーの希望は「Web Speech APIを使うこと」。以下の操作・実装順は提案であり、実機で成立した仕様とは区別する。既存設計の「アプリ内の音声認識を実装しない」はこの案の採用時に変更する。OS標準音声入力と手入力も引き続き使える。

## 2. 現在の実装との接点

- ノード編集は `ui-prototype/index.html` の `startEdit()` / `finishEdit()` と `contenteditable="plaintext-only"` を使う。`focusout` で確定するため、マイクボタンへのフォーカス移動で先に編集が閉じる問題を解決する必要がある。
- 指示欄は `#promptInput` のtextarea。認識結果を設定するだけでは通常の入力イベントは発生しないため、`draftVersion` の更新と `resizePrompt()` を通常入力と共通化する。
- 指示機能は `features.js` とローカル中継の設定で制御され、静的公開ではOFF。音声入力を指示機能から独立させ、公開版でもノードの追加・書きかえに使えるようにする。
- 手の操作は編集中・入力欄へのフォーカス中に抑止される。マイク操作中も抑止し、意図しない選択・ノード移動を避ける。
- 公開用の `ui-prototype/_headers` は `microphone=()`。音声入力の公開時に `microphone=(self)` への変更を検討・検証する。現在のNode中継はこのファイルをヘッダーとして適用していないため、ローカルでの成功だけでは公開構成の確認にならない。

## 3. 対応環境と処理先

MacのChromeを最初の検証環境にし、MacのSafariとiPadのSafariを次に確認する。SafariはWebKit公式に音声認識対応が案内されており、同記事ではSiriを有効にする必要があるとされる。ただし2021年の導入記事なので、現在の端末設定と挙動は実機で確認する。[WebKit公式](https://webkit.org/blog/11648/new-webkit-features-in-safari-14-1/)

コンストラクターは `window.SpeechRecognition || window.webkitSpeechRecognition` で検出する。存在しても、認識サービス・言語・権限・ネットワークの状態まで保証されないため、開始後の失敗も通常の操作として扱う。ブラウザ名だけで利用可能と決めない。[API仕様](https://webaudio.github.io/web-speech-api/)

基本方式ではブラウザの認識サービスへ音声が送られる可能性がある。独自の音声アップロードAPIやAPIキーは不要だが、オフライン動作や端末内処理は保証しない。端末内認識には `processLocally` と言語パックの仕組みがあるものの、日本語と対象端末での利用可能性を確認するまでは初期版の必須条件にしない。[仕様提案元の端末内認識の解説](https://github.com/WebAudio/web-speech-api/blob/main/explainers/on-device-speech-recognition.md)

画面には開始前から「音声はブラウザの音声認識サービスで処理される場合があります」と表示する。アプリ自身は音声を保存しない。指示欄を送信した場合のCodexへの文字・マップ送信は、音声認識とは別の処理として既存の説明を維持する。

## 4. 操作案

### ノードの追加・書きかえ

1. 既存の「子を追加」または「書きかえ」で編集を開く。
2. 編集中だけ表示する「音声入力」ボタンを押す。開始時点のノードID、マップのセッション、編集の識別子を固定する。
3. 「開始中」「聞き取り中」「終了処理中」を文字とボタン状態で示す。聞き取り中は同じ位置に「停止」を表示する。
4. 認識途中の文字は補助表示へ出し、最終結果だけを編集欄の下書きへ入れる。
5. 認識が終わっても編集欄を維持する。ユーザーが修正し、Enterまたは既存の確定操作で反映する。追加と初回の文字確定は現在と同じく1回のUndoにまとめる。

初期版はカーソル位置への挿入を避け、**開始時の下書きの末尾に追加**する。置きかえたいときは既存文字を手で消してから開始する。この規則をボタン付近で案内する。認識途中は対象欄の手入力を一時的に止め、終了後に修正できるようにする。既存文字を失敗時に失わない。

`focusout` の確定を「編集欄＋音声操作領域」の外へ移った場合に限定する。ポインターのフォーカス抑止だけに頼らず、キーボードのTab移動・読み上げ・iPadのタッチでもボタンに到達できる構成にする。

### 指示欄

指示機能がONの場合だけ、指示欄にも同じマイクボタンを置く。認識文字は末尾へ追加し、既存の4000文字制限を適用する。収まらない場合は全文を別の確認表示に保持し、自動切り捨てや自動送信をしない。認識終了後、通常どおり修正して送信する。

開始中・聞き取り中・終了処理中は送信を無効にし、Enterでも送らない。Codexの処理中・確認中は音声入力を開始できない。追加質問への回答待ちでは入力できるが、質問IDも対象として固定し、質問が変われば中断する。

## 5. 実装案

`ui-prototype/speech/controller.js` にブラウザAPIとの接続と状態管理を置き、ノードと指示欄は同じ制御を利用する。マップ・保存・Codexを音声認識モジュールから直接変更しない。

初期設定案：

```js
const Recognition = window.SpeechRecognition || window.webkitSpeechRecognition;
const recognition = new Recognition(); // 利用可否を確認した後に生成
recognition.lang = 'ja-JP';
recognition.continuous = false;
recognition.interimResults = true;
recognition.maxAlternatives = 1;
```

UIの表示言語と認識言語は分ける。まず日本語を使い、英語対応時に認識言語を明示的に選べるようにする。短い発話向けの設定と途中結果の扱いは[Chrome公式の実装例](https://developer.chrome.com/blog/voice-driven-web-apps-introduction-to-the-web-speech-api/)を参考にする。同記事は古いため、現在の互換性の保証には使わない。

状態は `idle → starting → listening → stopping → idle` を基本とし、エラーは終了理由として保持する。開始はユーザーのボタン操作内で `start()` を呼ぶ。同時に1セッションだけ動かし、自動再開・自動再試行はしない。

`result` ごとの文字列を単純に追記せず、結果のインデックスに対応した配列を更新し、開始時の下書きと最終結果から全文を組み立てる。途中結果は置き換え可能な補助表示に分離し、`innerHTML` を使わない。これにより同じ結果の重複挿入を避ける。

停止ボタンは `stop()` で最終結果を待ち、対象が有効なら下書きへ反映する。編集取消・マップ切替・ページ離脱・対象削除・閲覧専用への移行は `abort()` で中断する。対象欄から外へ移動して確定する場合も先に中断し、既に受け取った最終結果だけを既存の確定処理へ渡す。確定済みの編集へ遅い結果を書き戻さない。[停止・中断のAPI仕様](https://webaudio.github.io/web-speech-api/#speechreco-methods)

各セッションの識別子と対象の有効性をすべてのコールバックで検証する。中断時には先に識別子を無効化する。開始・停止が完了しない場合の上限時間を設け、仮に開始15秒・停止5秒で中断し、再操作できる状態に戻す。数値は実機確認で調整する。

タブ非表示と `pagehide` では必ず中断する。既存のwindow `blur` 処理をそのまま流用すると権限ダイアログによるフォーカス変化で初回開始を妨げる可能性があるため、音声入力では別途検証する。復帰時には自動再開しない。

## 6. 失敗時の表示

| 状況 | 挙動 |
| --- | --- |
| APIなし | マイクを無効表示し、「このブラウザでは利用できません」。手入力を継続できる |
| 権限拒否・サービス利用不可 | 下書きを保持。サイト・OSの権限や設定を確認する案内。自動で権限要求を繰り返さない |
| 音声なし・該当結果なし | 「聞き取れませんでした」。必要なら再度ボタンを押す |
| マイクなし・取得失敗 | 接続やほかのアプリの利用を確認する案内 |
| 通信失敗・言語未対応 | その原因を表示し、手入力へ戻れるようにする |
| ユーザーによる取消 | エラー表示なし。認識途中の文字を破棄する |
| 別の編集へ移動後の結果 | 結果を無視し、別ノードや別のマップに書き込まない |

途中で失敗しても、受け取った最終結果と開始前の下書きは残す。ノード編集全体の取消時だけ既存の取消規則へ戻す。途中結果を最終結果として扱わない。

## 7. 配信と検証

公開先は既存のHTTPS配信を使い、localhostでの開発と区別する。音声認識用のサーバー中継やライブラリ追加は基本的に不要。

公開前に `_headers` のマイク禁止設定を見直す。`microphone` ポリシーとSpeechRecognitionの関係はブラウザ実装も含めて確認し、ヘッダー変更だけで利用可能になるとは断定しない。既存のカメラ・位置情報の設定は維持する。

| 段階 | 確認内容・完了条件 |
| --- | --- |
| 1. APIの実機検証 | Mac Chrome・Mac Safari・iPad Safariで日本語の開始、初回許可、拒否、停止、無音、再開始を確認。OS・ブラウザ版、Siri設定、配信URLとヘッダーを記録 |
| 2. ノードへの接続 | 新規・既存ノードで音声→修正→確定→Undoが成立。Tabでマイクへ移動しても編集が閉じない。指示OFFでも利用できる |
| 3. 指示欄への接続 | 下書き・4000文字制限・追加質問に対応。認識中のEnter送信が起きず、完了後の手動送信で既存処理につながる |
| 4. 公開構成の確認 | ステージングHTTPSで配信ヘッダーと権限を確認。手の操作との併用、タブ移動、マップ切替、編集取消で別対象へ書き込まない |

自動テストは、偽の認識APIで結果の重複・途中結果の差し替え・中断後の遅延イベント・対象変更・開始停止タイムアウト・文字数超過を検証する。ブラウザ自動化はフォーカスと送信抑止を確認する。認識精度、実マイク、権限画面、Safariの成立性をモックテストで確認済みとは扱わない。

実装に進むときは、本体設計書6節、実装計画の音声入力のスコープ、Codex指示入力設計、配信設計のマイク権限とデータ処理の説明を合わせて更新する。
