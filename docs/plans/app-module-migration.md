# アプリの共有グローバル依存を減らす計画

2026年10月25日。編集確定・ツリー変更・操作許可・自動保存の共通化を土台に、依存関係を明示する。機能を追加せず、Undo/Redo、プレビュー、保存、AIとの競合条件を維持する。

## 第1段階：共通処理と画面の接続を分離（実装済み）

ブラウザでは名前付きAPIを公開し、Nodeでは `require()` できる、既存の共用モジュール形式を使用する。`core/` は `state`、DOM、他の共有APIを暗黙に参照しない。状態を持つ処理は `create()` ごとのクロージャーに閉じ込める。HTML上の読み込み順は画面との接続にのみ残る。

| モジュール | 明示する入力・依存 | アプリ側の接続 |
| --- | --- | --- |
| `core/operation-policy.js` | 操作状態の値、現在と期待するセッション／リビジョン | `app/operation-policy.js` が画面状態を収集する |
| `core/tree.js` | 各呼び出しのマップ | `app/tree.js` が現在のマップを渡す。DOMによるノード寸法取得はアプリに残す |
| `core/history.js` | `stacks`（`history`／`future`）、差分API、履歴上限、時計 | `app/history.js` が検証・操作中断・画面更新を担当し、`app/maps.js` は `load()` でログを切り替える |
| `core/autosave.js` | スナップショット取得、保存、失敗回復、状態通知、タイマー | `app/persistence.js` が保存先と画面を接続する。旧 `app/autosave.js` から移動 |

`MapEditHistory.create()` の公開APIは以下。

- `record(before, after)`：差分を登録する。Redoの分岐破棄と履歴上限を扱う。
- `restore(map, 'undo' | 'redo')`：スタックを移動し、復元したマップを返す。対象がなければ `null`。
- `load(map, log)`：ログを検証してスタック・連番・保存待ち差分を置き換える。
- `takeChanges()`／`retryChanges(batch)`：保存待ち差分の取得と失敗時の回復。取り消された分岐を再登録しない。

`stacks` はアプリと共有する明示的な依存であり、モジュールが参照するのは `history` と `future` のみ。マップ、DOM、保存先、AIクライアントにはアクセスしない。`record()` は検証済みのマップを受け取り、検証や自動保存を独自には行わない。

テストの実行対象は [app-scripts.cjs](../../tests/helpers/app-scripts.cjs) で明示する。画面操作テストはHTMLの内容から実行対象を抽出しない。一方で別のテストがHTMLの `core/`・`app/` の一覧と順序を照合するため、配信側とのずれを検出できる。

## 第2段階：画面側の状態と副作用を明示する（進行中）

2026年10月25日、コンテキストと履歴・保存の接続まで実装。

- `app/context.js` の `MindmapAppContext.create()` が、マップ状態・画面要素・サービス・タイマー・副作用コールバックをまとめる。呼び出しごとに履歴スタック、操作状態、タイマーハンドル、保存失敗の診断フラグを生成する。初期マップ・画面要素・サービス・タイマー関数は呼び出し側が別々に用意する。
- `app/history.js` と `app/persistence.js` は、DOMやアプリの共有スコープなしで読み込めるファクトリーへ変更した。`commit()` の検証・ロールバック・履歴登録、プレビュー中の確定済みスナップショット保存は維持する。
- `app/bootstrap.js` が画面処理のコールバックを接続してからファクトリーを生成する。従来の画面モジュールには、生成した操作APIの別名を提供して段階的に移行する。
- `tests/app-context.test.cjs` で、同一プロセス内の2コンテキストの編集、Undo/Redo、画面通知、保存先、タイマーの独立と、検証失敗・読み取り専用のロールバック、プレビュー中の保存、保存失敗後の分岐破棄を確認する。

残作業は、編集・画像・AI・マップ切り替えなどの画面処理をコンテキストと操作APIを受け取る形に移すこと。現時点の独立性の検証対象は履歴・保存のファクトリーであり、画面全体の複数起動はまだ完了条件を満たしていない。

`app/state.js` の画面要素、サービス、マップ状態、タイマーをアプリ生成時のコンテキストに分ける。`app/history.js` と `app/persistence.js` を、このコンテキストを受け取るファクトリーへ移す。`commit()` の検証・ロールバック・履歴登録の入口は維持する。

続いて編集、画像、AI、マップ切り替えを、共通の操作APIを受け取る形へ移す。現在相互に呼び出している画面処理は、初期化時にコールバックを接続する。モジュールの初期評価で別モジュールの画面処理を呼ばない。

完了条件：同じプロセス内でアプリの状態とサービスを別々に用意しても、編集や保存の状態が混ざらない。既存の画面操作テストを維持する。

## 第3段階：ES Modulesのエントリーポイントへ移す

画面側の暗黙の相互参照がなくなった段階で、`import`／`export` に変換し、HTMLからは単一の `type="module"` エントリーポイントを読む。サービスの既存ブラウザAPIは境界で受け取り、共通処理の内部では参照しない。Node共用コードとテストの読み込み方法を同時に切り替える。

完了条件：HTMLのスクリプト順で機能を組み立てず、エントリーポイントで依存を接続する。開発用配信と静的ビルドの双方で起動できる。

## 検証

共通処理と履歴・保存ファクトリーの単体テストはHTMLやアプリの共有スコープを使わず、モジュールを直接読み込む。ブラウザ向けAPIもDOMなしで順序を変えて評価する。ツリーのキャッシュ無効化、操作別の許可条件、履歴インスタンスの独立、Undo/Redo、保存失敗中の分岐破棄、ログ切り替えを確認する。

画面操作は従来の統合テストを継続する。実ブラウザの見た目や実カメラの精度は、この単体・統合テストの対象外。
