# アプリの共有グローバル依存を減らす計画

2026年10月25日。編集確定・ツリー変更・操作許可・自動保存の共通化を土台に、依存関係を明示する。機能を追加せず、Undo/Redo、プレビュー、保存、AIとの競合条件を維持する。

## 第1段階：共通処理と画面の接続を分離（実装済み）

ブラウザでは名前付きAPIを公開し、Nodeでは `require()` できる、既存の共用モジュール形式を使用する。`core/` は `state`、DOM、他の共有APIを暗黙に参照しない。状態を持つ処理は `create()` ごとのクロージャーに閉じ込める。HTML上の読み込み順は画面との接続にのみ残る。

| モジュール | 明示する入力・依存 | アプリ側の接続 |
| --- | --- | --- |
| `core/operation-policy.js` | 操作状態の値、現在と期待するセッション／リビジョン | `app/operation-policy.js` が画面状態を収集する |
| `core/tree.js` | 各呼び出しのマップ | `app/tree.js` が現在のマップを渡す。DOMによるノード寸法取得はアプリに残す |
| `core/history.js` | `stacks`（`history`／`future`）、差分API、履歴上限、時計 | `app/history.js` が検証・操作中断・画面更新を担当し、`app/maps.js` は `load()` でログを切り替える |
| `core/autosave.js` | スナップショット取得、保存、失敗回復、状態通知、タイマー | `app/persistence.js` が保存先と画面を接続する。旧 `app/autosave.js` から移動 |

`MapEditHistory.create()` の公開APIは以下。

- `record(before, after)`：差分を登録する。Redoの分岐破棄と履歴上限を扱う。
- `restore(map, 'undo' | 'redo')`：スタックを移動し、復元したマップを返す。対象がなければ `null`。
- `load(map, log)`：ログを検証してスタック・連番・保存待ち差分を置き換える。
- `takeChanges()`／`retryChanges(batch)`：保存待ち差分の取得と失敗時の回復。取り消された分岐を再登録しない。

`stacks` はアプリと共有する明示的な依存であり、モジュールが参照するのは `history` と `future` のみ。マップ、DOM、保存先、AIクライアントにはアクセスしない。`record()` は検証済みのマップを受け取り、検証や自動保存を独自には行わない。

テストの実行対象は [app-scripts.cjs](../../tests/helpers/app-scripts.cjs) で明示する。画面操作テストはHTMLの内容から実行対象を抽出しない。一方で別のテストがHTMLの `core/`・`app/` の一覧と順序を照合するため、配信側とのずれを検出できる。

## 第2段階：画面側の状態と副作用を明示する（実装済み）

2026年10月25日、コンテキストと履歴・保存に続き、編集・画像・AI・マップ切り替え・描画・入力・音声・カメラをインスタンスごとのファクトリーへ移した。

- `app/context.js` の `MindmapAppContext.create()` が、マップ状態 (`state`)、画面要素 (`elements`)、サービス (`services`)、ブラウザ環境 (`environment`)、画面の操作状態 (`ui`)、タイマー (`timers`)、副作用コールバック (`effects`) を分けて保持する。初期マップ・画面要素・サービスは呼び出し側が別々に用意する。
- 画面モジュールは `create(context, operations)` で生成する。編集・画像・AI・マップ切り替えも、明示的に渡された共通の操作APIを使う。`app/history.js` と `app/persistence.js` は前段階のファクトリーを維持し、`commit()` の検証・ロールバック・履歴登録と、プレビュー中の確定済みスナップショット保存を変更していない。
- `app/bootstrap.js` の `MindmapAppBootstrap.create({ environment, services, modules, map?, sessionId? })` が、全モジュールのAPIを接続してから `initialize()` でイベントを登録する。戻り値は `{ context, operations, start }`。モジュールの初期評価では画面や別のモジュールの処理を呼ばない。
- `app/browser.js` が既存のブラウザAPIを受け取り、アプリごとの画像ストアとAIクライアントを生成する。`app/main.js` はこの境界を呼び出し、`start()` で `app/startup.js` の初期描画・ストレージ起動を開始する。画面処理の共有グローバル変数への別名は配信コードから取り除いた。
- パレット、画像選択・表示、AIのUndoボタン、マップ一覧・監視、カメラ、ドラッグ・アニメーション、通知の状態もインスタンスに閉じる。アイコンパレットは環境と翻訳サービスを受け取り、各アプリのDOM・イベント・通信を利用する。

`tests/app-context.test.cjs` は履歴・保存単位の独立性を確認する。`tests/app-instances.test.cjs` は同じモジュール定義を再利用して2つのアプリを生成し、別々のDOM・サービスで以下を確認する。

- 編集イベント、Undo/Redo、保存失敗・回復、保存先、タイマーが混ざらない。
- 一方のマップ切り替えが、他方の未確定編集や保存ログを変更しない。
- 画像保存の待機中に他方のマップが切り替わっても、元の対象へだけ画像を適用する。
- AIの応答・Undoボタン・入力中の下書きが独立する。切り替え前の遅い応答を拒否し、他方のAI処理を中断しない。
- パレット、カメラ、ポインターと、起動時のストレージ・一覧監視が各アプリの環境を利用する。

従来の画面操作テストは [ui-app.cjs](../../tests/helpers/ui-app.cjs) のアダプターから実際の生成処理を呼び出して維持する。旧名でのテスト操作を支える別名は、このテスト用アダプターにだけ置く。全画面ファクトリーについて、DOMやサービスを用意せず、正順・逆順での評価とNodeからの直接読み込みも検証する。

完了条件：同じプロセス内でアプリの状態とサービスを別々に用意しても、編集や保存の状態が混ざらない。既存の画面操作テストを維持する。上記のインスタンステストと既存テストで確認済み。

## 第3段階：ES Modulesのエントリーポイントへ移す

画面側の暗黙の相互参照がなくなった段階で、`import`／`export` に変換し、HTMLからは単一の `type="module"` エントリーポイントを読む。サービスの既存ブラウザAPIは境界で受け取り、共通処理の内部では参照しない。Node共用コードとテストの読み込み方法を同時に切り替える。

完了条件：HTMLのスクリプト順で機能を組み立てず、エントリーポイントで依存を接続する。開発用配信と静的ビルドの双方で起動できる。

## 検証

共通処理と画面ファクトリーの単体テストはHTMLやアプリの共有スコープを使わず、モジュールを直接読み込む。ブラウザ向けAPIもDOMなしで順序を変えて評価する。ツリーのキャッシュ無効化、操作別の許可条件、履歴インスタンスの独立、Undo/Redo、保存失敗中の分岐破棄、ログ切り替えを確認する。

画面操作は従来の統合テストを継続する。実ブラウザの見た目や実カメラの精度は、この単体・統合テストの対象外。
